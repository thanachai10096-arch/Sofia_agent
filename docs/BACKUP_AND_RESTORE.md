# Sofia Agent backup and restore contract

## Status

The versioned integrity-manifest primitives in `src/platform/backup-manifest.ts` and the explicit-source coordinator in `src/platform/backup-coordinator.ts` are initial building blocks, not a complete backup/restore feature. The coordinator can collect caller-supplied in-memory snapshots, verify the resulting bundle, and export a verified bundle as a private directory tree using `writeBackupBundleDirectory()`, then re-read and verify it with `readBackupBundleDirectory()` without following symlinks or accepting unlisted files/directories (including empty directories); directory export/import is not a compressed archive and does not restore state. `stageBackupBundleForRestore()` now writes a verified bundle into a new private staging directory, verifies the on-disk copy, and returns an explicit cleanup function; it still does not apply the staged data to live stores. `preflightBackupRestore()` now creates a deterministic, non-mutating restore plan from explicit target/path assignments; it verifies the complete bundle first and rejects unassigned paths, overlapping ownership, duplicate target names, and paths absent from the manifest. It does not invoke restore adapters or change live state. `executeBackupRestoreTransaction()` adds an adapter-driven execution contract: it runs every adapter preflight, captures every rollback snapshot before the first apply, applies targets in deterministic order, and attempts rollback in reverse order (including the target whose apply rejected). Rollback failures are surfaced alongside the original apply failure. This is best-effort coordination, not a cross-store atomic transaction; production adapters still need store-specific, tested snapshot/rollback behavior. An explicit adapter now snapshots the existing file-backed project-memory store without scanning its directory; missing memory produces an empty source. `directoryBackupRestoreAdapter()` now provides a tested restore adapter for selected regular files beneath an existing root: it rejects symlink traversal, atomically replaces files, and captures byte-for-byte rollback snapshots. This adapter is appropriate for file-backed memory, not an open SQLite database. A second explicit adapter snapshots only a caller-selected user's file-backed memory; its source name and manifest path use a SHA-256 identity hash, and it does not enumerate other users. It still does not discover all stores, write an archive, encrypt data, or restore state. `SqliteSessionStore.createConsistentSnapshot()` now creates an isolated SQLite snapshot using SQLite `VACUUM INTO`, so committed WAL content is included without copying live database files or sidecars. The snapshot helper refuses existing destinations and does not overwrite them.

## Manifest

- Format identifier: `sofia-agent-backup`
- Current format version: `1`
- Each entry records a normalized relative POSIX path, byte length, and SHA-256 digest.
- Entries are sorted by path for deterministic manifests.
- Manifest parsing rejects unsupported versions, duplicate paths, traversal and absolute paths, malformed digests, excessive entry counts, and excessive declared sizes.
- Verification fails closed when files are missing, unexpected, truncated, changed, or use unsafe paths.

## Required before production restore

1. **Explicit scope:** enumerate supported stores and exclude credentials, environment files, API keys, tokens, and provider secrets by default.
2. **Consistent snapshot:** use store-specific snapshots or quiesce writers. The session store offers `createConsistentSnapshot()` using SQLite `VACUUM INTO`, and `sqliteSessionBackupSource()` stages a private temporary snapshot and removes it after reading; the file-backed project-memory store and selected-user memory store expose read-only snapshot contracts; every other persistent store still needs its own snapshot contract. Never copy a live SQLite database without coordinating WAL/SHM.
3. **Private output:** create backup directories/files with restrictive permissions and never log file contents or secrets.
4. **Archive defenses:** if archives are added, reject absolute paths, traversal, symlinks/hardlinks, duplicate normalized paths, and decompression bombs before extraction.
5. **Verify before mutation:** validate the complete manifest and every byte count/checksum before touching destination state.
6. **Safe restore:** `stageBackupBundleForRestore()` provides a verified private staging directory. `executeBackupRestoreTransaction()` coordinates adapter preflight, rollback snapshots, deterministic application order, and reverse-order rollback. `directoryBackupRestoreAdapter()` is available for selected regular files under an existing root, with symlink checks and same-directory atomic file replacement. It is not a database-aware SQLite restore and is not a cross-store atomic commit; SQLite needs a separate lifecycle-aware adapter, and all destination writers still require operational testing.
7. **Version compatibility:** reject unknown future versions; migrations must be additive and tested on copied fixtures.
8. **Recovery tests:** test truncated/corrupt files, checksum mismatch, duplicate paths, malicious paths, interrupted restore, disk-full errors, SQLite WAL state, and rollback behavior.
9. **Portability:** document OS-specific state paths and keep credentials out of exported bundles. A manifest checksum detects accidental changes but is not a signature and does not prove authenticity.

Do not describe Sofia as having complete automated backups until archive creation, consistent store snapshots, restore staging/rollback, and end-to-end tests exist.
